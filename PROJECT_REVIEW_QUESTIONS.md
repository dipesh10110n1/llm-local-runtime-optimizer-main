# Orbit project review question bank

Use the short answer first, then offer the detail if invited. “Evidence” refers to repository evidence, not a claim that every path was run live.

## Project fundamentals

### 1. What problem does Orbit solve?
**Short:** It selects a safe local LLM configuration using recorded quality and cost evidence instead of choosing only the fastest or largest model.  
**Detail:** It combines hard constraints—quality, latency, RAM and actual energy when present—with benchmark profiles and an explicit cost ordering.  
**Evidence:** `optimizer/optimizer.py`, `optimizer/calibrated_profiles.py`.  
**Follow-up:** Is it globally optimal? Only within the completed, comparable evidence set.

### 2. Why use a local LLM instead of a cloud model?
**Short:** Privacy, offline operation, predictable local control, and the ability to measure local resource trade-offs.  
**Detail:** Local inference keeps prompts/models on the machine and enables configuration-level CPU/RAM measurements; cloud systems can be stronger but move the control boundary and hide infrastructure metrics.  
**Evidence:** `docs/RESPONSIBLE_AI.md`, loopback settings in `core/settings.py`.  
**Follow-up:** Does local automatically mean secure? No; local logs and physical access still need governance.

### 3. Who is the intended user?
**Short:** A developer or technical user running open local models on constrained hardware.  
**Detail:** The UI exposes RAM reserve, model comparison, task-valid quality gates and evidence rather than presenting an opaque chatbot-only choice.  
**Evidence:** `dashboard.py`, `api/app.py`.  
**Follow-up:** Is it a consumer cloud assistant? No.

### 4. Why optimize quality, latency, and energy together?
**Short:** A fast answer that is wrong is not useful, and a high-quality answer that cannot run safely is not deployable.  
**Detail:** These objectives conflict: larger/less-quantized models can cost more RAM/latency; actual energy must be separately measured.  
**Evidence:** constraint fields in `api/app.py`; profiles in `optimizer/calibrated_profiles.py`.  
**Follow-up:** Is lower latency proof of lower energy? No.

## Architecture

### 5. Describe the architecture in one sentence.
**Short:** Streamlit/FastAPI send a local request through an evidence-aware optimizer, a RAM-safe llama.cpp manager, prompt pipeline, evaluator, and telemetry store.  
**Detail:** JSONL is primary evidence; MySQL is a non-blocking mirror.  
**Evidence:** `dashboard.py`, `api/app.py`, `runtime/`, `optimizer/`, `database/`.  
**Follow-up:** Which component makes the final choice? `Optimizer.recommend()` or `compare_on_spot()` for live comparison.

### 6. How does a dashboard prompt become an answer?
**Short:** It is compared or selected, prepared, generated by the local server, measured, and displayed with its decision metadata.  
**Detail:** `dashboard.py` calls `compare_on_spot`; each safe candidate runs sequentially and the winning already-generated draft is displayed.  
**Evidence:** `dashboard.py`, `optimizer/live_comparator.py`.  
**Follow-up:** Why not regenerate the winner? It could differ from the response that was measured.

### 7. Why are API and dashboard both present?
**Short:** The dashboard supports human review; the API supports reproducible programmatic access.  
**Detail:** Both use common optimizer/runtime modules rather than two model-selection implementations.  
**Evidence:** `api/app.py`, `dashboard.py`.  
**Follow-up:** Is FastAPI public by default? Deployment instructions bind it to loopback.

### 8. What is the source of truth for experiments?
**Short:** Timestamped JSONL records.  
**Detail:** MySQL mirrors useful queryable telemetry but failures never block inference or evidence recording.  
**Evidence:** `database/telemetry.py`, `docs/JSONL_PRIMARY_STORE.md`.  
**Follow-up:** Why not only use MySQL? Local JSONL is simpler, portable, and keeps raw evidence close to the run.

## Python implementation

### 9. How are models discovered?
**Short:** The registry combines `config/models.json` with recursively discovered valid-header `.gguf` files.  
**Detail:** Qwen filenames are parsed for size/quantization; unknown GGUF files are conservatively labelled unknown.  
**Evidence:** `core/model_registry.py:load_models`.  
**Follow-up:** Does a GGUF header prove model quality/architecture? No.

### 10. How do you avoid killing someone else’s model server?
**Short:** Orbit stops only the PID stored as its managed runtime after checking its name is `llama-server`.  
**Detail:** It can adopt exactly one project-model server, but refuses an unowned running server.  
**Evidence:** `runtime/supervisor.py:_stop_managed_server`, `_adopt_project_server`.  
**Follow-up:** Why is that conservative? A false positive could terminate unrelated work.

### 11. How is RAM safety calculated?
**Short:** It estimates model file memory plus runtime/KV overhead and keeps a configurable reserve.  
**Detail:** `1.3 × GGUF MiB + 300 + 0.15 × context`; measured RSS later replaces estimates as evidence.  
**Evidence:** `optimizer/live_matrix.py:required_memory_mb`.  
**Follow-up:** Is that formula exact? No; it is an admission estimate.

### 12. How are errors handled?
**Short:** Runtime/network exceptions become structured unavailable outcomes rather than recommendations.  
**Detail:** Benchmark runners retain failures, and the API maps unsafe/missing conditions to HTTP errors.  
**Evidence:** `runtime/clients.py`, `api/app.py`, benchmark runners.  
**Follow-up:** Are all failures automatically recoverable? No; model/runtime repair is an operator action.

## LLM fundamentals

### 13. What is inference?
**Short:** Repeatedly predicting the next token from the prompt and prior generated tokens.  
**Detail:** It differs from training: Orbit never trains models; it serves frozen GGUF weights locally.  
**Evidence:** `runtime/clients.py:generate`.  
**Follow-up:** Why does output length matter? More generated tokens increase latency and energy opportunity.

### 14. What is a token?
**Short:** A model-specific text unit, often smaller than a word.  
**Detail:** Orbit asks llama.cpp’s tokenizer when supported and otherwise records token count as unavailable.  
**Evidence:** `runtime/clients.py:tokenize`.  
**Follow-up:** Why not use character count? It is not an exact model token count.

### 15. What is the context window?
**Short:** The maximum prompt/history tokens a model can attend to in one request.  
**Detail:** Larger contexts increase KV-cache memory and prompt-processing work; Orbit tests 1024/2048/4096 settings.  
**Evidence:** `config/benchmark_matrix.json`.  
**Follow-up:** Does a model’s 32768 advertised limit mean the laptop can safely use it? No.

### 16. What is temperature?
**Short:** A sampling control: lower values make output more deterministic.  
**Detail:** Benchmarks use zero to reduce generation randomness; the dashboard exposes a user-selected value for normal conversation.  
**Evidence:** `benchmarks/full_matrix_benchmark.py`, `dashboard.py`.  
**Follow-up:** Does temperature zero guarantee identical output? It reduces variability but runtime/system factors can still matter.

## Quantization

### 17. What is quantization?
**Short:** Representing model weights with fewer bits to reduce storage and memory.  
**Detail:** It commonly trades numerical precision for RAM and potentially speed; quality impact must be measured on the task.  
**Evidence:** Q4/Q5/Q6 models and `benchmarks/quantization_comparison.py`.  
**Follow-up:** Does lower-bit always lower energy? No.

### 18. What are Q4_K_M, Q5_K_M and Q6_K here?
**Short:** Three GGUF quantization variants of the same Qwen 1.5B base model.  
**Detail:** They represent increasing file size/precision and are suitable for a controlled within-base study.  
**Evidence:** `models/quantizations/`, `docs/MODEL_SOURCES.md`.  
**Follow-up:** Can they prove comparison across different model families? No.

### 19. Why Qwen?
**Short:** The repository contains Qwen2.5 instruct GGUF variants across useful sizes and quantizations.  
**Detail:** Same-family availability supports controlled comparisons; do not claim it is universally best without external/task evidence.  
**Evidence:** `config/models.json`, model inventory.  
**Follow-up:** Why not Llama/Mistral? They are reasonable alternatives but are not the implemented benchmark set.

### 20. What actual quantization evidence exists?
**Short:** A logged Q4/Q5/Q6 Spider study with 15 requests per variant.  
**Detail:** It uses five development examples and three trials, so it supports a narrow controlled observation—not general accuracy.  
**Evidence:** `logs/quantization_comparisons/*210533*.summary.json`.  
**Follow-up:** Why are all scores sometimes high? Small samples can be easy; inspect raw records and expand coverage.

## llama.cpp and Ollama

### 21. Why llama.cpp?
**Short:** It is the primary CPU-friendly local GGUF runtime and exposes server timings and cache controls.  
**Detail:** Orbit starts `llama-server` on loopback, uses streaming OpenAI-compatible chat completions, and can call `/tokenize`.  
**Evidence:** `runtime/supervisor.py`, `runtime/clients.py`.  
**Follow-up:** Was it live-verified today? No; the last readiness check found no available server.

### 22. Why not use only Ollama?
**Short:** Ollama is supported as an optional backend, but llama.cpp provides direct GGUF/process/cache benchmarking control used by the main harness.  
**Detail:** Ollama has a separate `/api/generate` path and opt-in live test.  
**Evidence:** `runtime/clients.py`, `inference/backends.py`, `tests/test_live_inference.py`.  
**Follow-up:** Can benchmarks compare backend differences fairly? Only with controlled identical settings/workloads.

### 23. What is model loading time versus inference time?
**Short:** Loading initializes model/server; inference generates a specific answer.  
**Detail:** Full-matrix records `runtime_activation_seconds` separately from end-to-end generation telemetry.  
**Evidence:** `benchmarks/full_matrix_benchmark.py`.  
**Follow-up:** Should loading time be included in every request latency? Usually report separately, depending on deployment scenario.

### 24. What is TTFT?
**Short:** Time from request start to the first generated text token.  
**Detail:** It reflects perceived responsiveness and can improve with prompt cache even if total generation time is similar.  
**Evidence:** `runtime/clients.py:generate`.  
**Follow-up:** Is TTFT the same as total latency? No.

## Optimization algorithm

### 25. How are hard constraints applied?
**Short:** Candidates violating requested quality, latency, RAM, or actual energy are rejected.  
**Detail:** Missing a requested metric is a violation, which prevents pretending unavailable data passes.  
**Evidence:** `optimizer/constraint_manager.py:violations`.  
**Follow-up:** What quality value is used? The lower confidence bound when available.

### 26. How does the quality threshold prevent low-quality selection?
**Short:** It is an admission gate before cost ranking.  
**Detail:** Repeated profiles use conservative lower confidence bound; a live Spider request requires a supplied gold reference.  
**Evidence:** `calibrated_profiles.select_lowest_cost`, `live_comparator.compare_on_spot`.  
**Follow-up:** Does this work for general chat? Not yet; general task evidence is absent.

### 27. How do you select “lowest cost” without hidden weights?
**Short:** After the gate, Orbit uses a documented lexicographic ordering.  
**Detail:** Balanced/latency prefers lower latency, then RAM, then higher throughput; energy-first needs physical joules.  
**Evidence:** `optimizer/calibrated_profiles.py:_cost_key`.  
**Follow-up:** Is there still a live weighted comparator? Yes, for on-the-spot measured responses; it is disclosed and not equivalent to historical global optimization.

### 28. How do you know the optimizer selects the best model?
**Short:** Only among the comparable, measured profiles it is given.  
**Detail:** It does not prove all untested candidates or arbitrary tasks; coverage and evidence limits are shown.  
**Evidence:** `docs/EXPERIMENT_PROTOCOL.md`, profile coverage fields.  
**Follow-up:** What would prove it better? A completed predefined matrix and baseline comparison.

## Benchmarking

### 29. Why have warm-up runs?
**Short:** First runs include initialization/cold-cache effects that should not be mixed with steady-state measurements.  
**Detail:** Runners label warm-up separately and exclude it from measured profile aggregation.  
**Evidence:** `full_matrix_benchmark.py`, `calibrated_profiles.py`.  
**Follow-up:** Are cold starts unimportant? No; report them separately for user experience.

### 30. Why repeat trials?
**Short:** Performance and generation can vary because of cache, scheduling, thermal state, and workload.  
**Detail:** Profiles calculate mean/median/stddev and a quality lower confidence bound when enough trials exist.  
**Evidence:** `optimizer/calibrated_profiles.py`.  
**Follow-up:** Is three trials statistically ideal? It is a minimum prototype threshold, not a strong final study.

### 31. What does the full matrix cover?
**Short:** Threads, context, cache mode, compression mode, and retrieval on/off across local models.  
**Detail:** It is a 144-configuration matrix per model before RAM filtering.  
**Evidence:** `config/benchmark_matrix.json`, `configuration_catalog.py`.  
**Follow-up:** Was every configuration completed? No; logs include deferred and RAM-safety skips.

### 32. Why preserve failures and skips?
**Short:** They are evidence of feasibility boundaries, not data to hide.  
**Detail:** A RAM skip proves a candidate was not safely runnable under the selected reserve; it is not a zero-quality score.  
**Evidence:** `full_matrix_benchmark.py`.  
**Follow-up:** Can skipped models be ranked? No.

## Quality evaluation

### 33. How is Spider quality evaluated?
**Short:** The generated SQL is compared to reference SQL and, when possible, read-only executed against the local matching SQLite database.  
**Detail:** Result equality accounts for reference ordering; non-read-only SQL is refused.  
**Evidence:** `optimizer/task_quality.py`.  
**Follow-up:** Why is execution matching stronger than exact SQL string matching? Equivalent SQL can differ textually.

### 34. Is Spider general LLM accuracy?
**Short:** No; it measures text-to-SQL on its schemas/questions.  
**Detail:** It is useful for a task-specific quality gate only.  
**Evidence:** `docs/LIMITATIONS.md`.  
**Follow-up:** How would you measure general reasoning? Run a held-out task-specific set such as GSM8K.

### 35. Are GSM8K/MMLU/IFEval integrated?
**Short:** Local preparation and runner code exists, but no completed standard-quality benchmark logs exist.  
**Detail:** GSM8K and MMLU scorers exist; IFEval is deliberately unavailable until its official checker is integrated.  
**Evidence:** `benchmarks/standard_quality_benchmark.py`, `quality_metrics/metrics.py`.  
**Follow-up:** Why not use the IFEval heuristic? It could overstate instruction following.

### 36. Why does unavailable quality fail a threshold?
**Short:** Passing without evidence would be an unsupported claim.  
**Detail:** It is safer to return no feasible recommendation than invent quality.  
**Evidence:** `constraint_manager.py`, `live_comparator.py`.  
**Follow-up:** Is unavailable the same as poor quality? No; it means not measured.

## Caching and compression

### 37. What is prompt caching in this project?
**Short:** llama.cpp reuse of prompt processing for a repeated prompt.  
**Detail:** It is enabled/disabled by server flags and tested as cold versus immediate identical warm repeat.  
**Evidence:** `cache_prompt_experiments.py`, `configuration_catalog.py`.  
**Follow-up:** Is it response caching? No.

### 38. Why compare cold and warm runs?
**Short:** Otherwise cache benefits can be confused with ordinary runtime variation.  
**Detail:** The study force-restarts before cold request, then immediately repeats the same prompt for warm request.  
**Evidence:** `cache_prompt_experiments.py:run`.  
**Follow-up:** Can cache affect correctness? It should not; quality is still recorded.

### 39. What compression is implemented?
**Short:** Whitespace normalization and conservative blank-line reduction.  
**Detail:** Conservative mode protects code/SQL indentation; neither is semantic summarization.  
**Evidence:** `runtime/prompt_pipeline.py:compress_prompt`.  
**Follow-up:** Does it guarantee fewer tokens? No; exact tokens require the model tokenizer.

### 40. What could go wrong with compression?
**Short:** It can remove formatting or implicitly change task meaning.  
**Detail:** That is why quality must be compared on the same workload, not inferred from shorter text.  
**Evidence:** `prompt_compression_experiment.py`.  
**Follow-up:** What is the safe default? `none`.

## Retrieval and Spider

### 41. Is this a vector RAG system?
**Short:** No; it is deterministic local lexical retrieval.  
**Detail:** It chunks text and ranks token-overlap, returning paths/chunk IDs.  
**Evidence:** `runtime/prompt_pipeline.py:retrieve`.  
**Follow-up:** Why use lexical retrieval? It is local, transparent, dependency-light, but weaker semantically.

### 42. How does retrieval avoid gold-SQL leakage in Spider tests?
**Short:** The Spider corpus builder uses schema metadata only and records that it contains no gold SQL.  
**Detail:** The prompt still needs model-generated SQL; the gold query remains evaluator-only.  
**Evidence:** `local_retrieval_benchmark.py:build_schema_corpus`.  
**Follow-up:** Is schema retrieval automatically grounding proof? No.

### 43. What is `tables.json` in Spider?
**Short:** Dataset-level schema metadata describing tables, columns, and relationships.  
**Detail:** Orbit’s prompt builder reads live local SQLite schema for a DB; verifier checks Spider structure.  
**Evidence:** `spider_data/.../tables.json`, `spider_verifier.py`.  
**Follow-up:** Why not include the whole DB? The schema is enough for query construction and much smaller.

### 44. Why only allow SELECT/WITH/EXPLAIN in evaluation?
**Short:** To prevent model output from modifying the evaluation database.  
**Detail:** The evaluator opens SQLite read-only and rejects write statements before execution.  
**Evidence:** `optimizer/task_quality.py:_safe_select`, `_execute_read_only`.  
**Follow-up:** Is it a hardened general SQL sandbox? No.

## RAM and hardware

### 45. What happens when RAM is insufficient?
**Short:** The candidate is skipped with a clear RAM-safety reason.  
**Detail:** The code retains reserve memory and may reuse an already loaded Orbit model only in explicit resident fallback mode.  
**Evidence:** `request_router.py`, `live_matrix.py`.  
**Follow-up:** Why not force model loading? It risks OS instability or swapping, corrupting benchmark validity.

### 46. Why is peak RSS measured?
**Short:** Actual process memory validates or improves on a pre-launch estimate.  
**Detail:** It is sampled during generation and stored per trial, but does not represent every process on the machine.  
**Evidence:** `runtime/clients.py:_ResourceMonitor`.  
**Follow-up:** Is it exact peak at microsecond resolution? No; sampling is periodic.

### 47. Does the project use GPU inference?
**Short:** The controlled configurations are CPU-only (`gpu_layers: 0`).  
**Detail:** Hardware profiling reports GPU devices but does not claim GPU energy/throughput experiments.  
**Evidence:** `configuration_catalog.py`, `hardware/hardware_profiler.py`.  
**Follow-up:** Could GPU support be added? Yes, with separate fair benchmarks.

### 48. Why preserve a RAM reserve?
**Short:** The OS, UI, database, and background processes need headroom.  
**Detail:** A model that exactly fills currently available RAM is unreliable and distorts results via paging.  
**Evidence:** `core/settings.py`, dashboard reserve slider.  
**Follow-up:** Is reserve fixed? Configurable, default 512 MiB.

## Energy and sustainability

### 49. Is the project’s energy result actual measurement or estimate?
**Short:** Currently proxy/estimate unless an approved physical cumulative-joule meter is configured.  
**Detail:** The bundled simulated meter is explicitly rejected from the measured path.  
**Evidence:** `hardware/energy_capability.py`, `hardware/meter_export.json`.  
**Follow-up:** Why be strict? Calling a proxy measured energy would invalidate sustainability claims.

### 50. What is the difference between watts and joules?
**Short:** Watts are rate of power; joules are accumulated energy.  
**Detail:** `energy = average power × duration`; `1 Wh = 3600 J`.  
**Evidence:** `docs/RESPONSIBLE_AI.md` measurement taxonomy.  
**Follow-up:** Can CPU percent be converted to joules exactly? No.

### 51. What does energy per token require?
**Short:** Valid physical joules and a valid generated-token count.  
**Detail:** It should use same workload and measured boundaries; otherwise it is only a proxy ratio.  
**Evidence:** `runtime/clients.py`, profile energy fields.  
**Follow-up:** Why not include prompt tokens? Report separately when analyzing full request cost.

### 52. Does quantization always reduce energy?
**Short:** No.  
**Detail:** Smaller weights can reduce memory traffic, but changed throughput, CPU utilization, load time, and quality can reverse the outcome.  
**Evidence:** Quantization study records proxy only; governance docs prohibit this inference.  
**Follow-up:** What proves it? Physical meter trials under controlled workload.

## MySQL and telemetry

### 53. Why JSONL plus MySQL?
**Short:** JSONL preserves local raw evidence simply; MySQL supports structured historical queries.  
**Detail:** MySQL is optional and non-blocking, preventing a database outage from stopping local inference.  
**Evidence:** `database/telemetry.py`, `database/repository.py`.  
**Follow-up:** Which is authoritative? JSONL.

### 54. What does one telemetry record contain?
**Short:** IDs/timestamps, model/configuration/provenance, prompt/trial state, quality, timing, memory, energy taxonomy, and errors.  
**Detail:** Exact shape varies by benchmark but raw full-matrix records are most complete.  
**Evidence:** `full_matrix_benchmark.py:_record`.  
**Follow-up:** Is response text always stored? Live selection text is redacted by default.

### 55. How are actual and proxy energy kept distinct?
**Short:** Separate `energy_joules` and `energy_proxy_joules` fields plus kind/method/measured flag.  
**Detail:** This prevents an estimated value being stored in an actual-energy field.  
**Evidence:** `database/schema.py:EnergyMetric`, `database/repository.py`.  
**Follow-up:** Can proxy rank a candidate? No.

### 56. What is the role of SQLite?
**Short:** It is used for read-only Spider database evaluation and isolated repository tests.  
**Detail:** It is not the main production telemetry design in this repository.  
**Evidence:** `task_quality.py`, `tests/test_mysql_telemetry.py`.  
**Follow-up:** Could SQLite replace MySQL for a prototype? Yes, if justified as a local-only deployment choice.

## Responsible AI

### 57. What makes Orbit Responsible AI rather than just a benchmark dashboard?
**Short:** It exposes constraints, evidence limits, rejection reasons, privacy defaults, and measurement taxonomy before automating a recommendation.  
**Detail:** It refuses unsupported quality/energy claims rather than filling missing data with optimistic values.  
**Evidence:** `docs/RESPONSIBLE_AI.md`, constraints and energy code.  
**Follow-up:** Is transparency alone enough? No; it also needs valid experiments and safe failure handling.

### 58. How does the user retain oversight?
**Short:** They can inspect candidates, constraints, telemetry, alternatives and override model selection.  
**Detail:** An override is visible as such; it is not silently presented as the historical optimum.  
**Evidence:** `api/app.py`, `dashboard.py`.  
**Follow-up:** Can override bypass quality evidence? It can generate, but must not be represented as quality-gated recommendation.

### 59. How is privacy handled?
**Short:** The intended inference path is local loopback and live response text is redacted from selection history by default.  
**Detail:** Datasets/benchmark outputs still require careful local handling and licensing.  
**Evidence:** `request_router.py:record_selection`, `docs/RESPONSIBLE_AI.md`.  
**Follow-up:** Are private prompts safe to put in benchmark JSONL? No.

### 60. How do you compare models fairly?
**Short:** Same task set, prompt template, runtime settings, warm-up policy, trials, and measurement method.  
**Detail:** Same-base quantization comparisons are fairer than unrelated model-family comparisons; incomplete coverage is disclosed.  
**Evidence:** `docs/EXPERIMENT_PROTOCOL.md`, quantization runner.  
**Follow-up:** Does comparing different sizes remain useful? Yes, if conditions and scope are explicit.

## Limitations and future scope

### 61. What is the biggest limitation today?
**Short:** The central optimizer is limited by incomplete comparable benchmark evidence, especially outside Spider.  
**Detail:** The code can select among profiles, but a global claim needs a completed declared matrix and general task evaluations.  
**Evidence:** `logs/full_matrix_benchmarks/`, no standard quality result files.  
**Follow-up:** What is first priority? Restore/verify llama.cpp and run a controlled minimum evidence campaign.

### 62. What should you never claim?
**Short:** Do not claim actual energy measurement, general quality, full-matrix optimality, or live end-to-end success unless those runs were executed.  
**Detail:** Proxy metrics, small pilots, and source code are not equivalent to validated results.  
**Evidence:** `docs/LIMITATIONS.md`, current readiness state.  
**Follow-up:** What can you claim? Implemented safeguards, recorded narrow studies, tests, and transparent limitations.

### 63. What would make it demonstration-ready?
**Short:** A working local runtime, completed declared benchmark subset, validated task-quality suites, physical meter or explicit energy-unavailable demo, and a repeatable deployment run.  
**Detail:** The demo should show discovery -> constraints -> profile recommendation -> exact runtime execution -> telemetry -> dashboard explanation.  
**Evidence:** `docs/DEPLOYMENT_RUNBOOK.md`, `docs/EXPERIMENT_PROTOCOL.md`.  
**Follow-up:** Must every optional feature be complete? No; core claims must be validated and limits clear.

### 64. Why is this an optimizer rather than only a dashboard?
**Short:** It applies hard feasibility constraints and an objective to choose a configuration, then explains the choice.  
**Detail:** A dashboard only visualizes results; Orbit’s optimizer consumes profiles, rejects violations, and feeds the selected exact configuration into runtime execution.  
**Evidence:** `optimizer/optimizer.py`, `api/app.py`.  
**Follow-up:** When is it only a dashboard? When no valid profiles exist and it merely displays measurements.
